# ОПТП СКО — база по пожарным подразделениям

Изменения подготовлены в ветке `feature/fire-unit-filter` для проверки через Pull Request. Ветка `main` и рабочая база Supabase не изменяются.

## Установка

1. Получите ветку `feature/fire-unit-filter` из репозитория и проверьте изменения Pull Request.
2. Проверьте интерфейс локально через HTTP-сервер, сохранив текущую конфигурацию Supabase.
3. На тестовой базе с копией действующей схемы проверьте SQL, RLS и доступ гостя/редактора. Миграция здесь не выполнялась: подключения к PostgreSQL нет.
4. После резервной копии выполните `supabase/migrations/202611060001_fire_units.sql` вручную. Миграция транзакционная; повторный запуск останавливается без изменений. При занятой таблице действует таймаут блокировки 5 секунд.
5. Выполните `supabase/migrations/202611060002_seed_fire_units.sql`: справочник заполнится 27 подразделениями из предоставленного `Список.docx`. Исправлен только пропущенный пробел в «СПЧ-5 УЧС г. Петропавловска»; остальные названия сохранены. Повторное выполнение не дублирует совпадающие названия и не меняет существующие записи или закрепления. Справочник доступен только для чтения клиенту; изменения через SQL Editor.
6. Редактор или администратор закрепляет объект через поле «Закреплённое подразделение» в существующей форме. Старые объекты остаются незакреплёнными. Существующие RLS на объектах продолжают определять права записи; фильтр не является ограничением доступа.

Выбор подразделения показывает закреплённые ОПТП. Ввод в общий поиск переключает на все подразделения; последующий выбор подразделения уточняет результаты. Поиск охватывает название, адрес, район и название подразделения. При отсутствии миграции просмотр существующих карточек сохраняется, запись поля закрепления отключается. Документы и схемы не мигрируются, storage/config.js не меняются.

## Откат

Предпочтителен возврат предыдущего фронтенда с сохранением новых таблицы и поля. Полное удаление схемы после начала закрепления потеряет связи; сначала экспортируйте `id, fire_unit_id` из объектов и весь справочник. До заполнения данных можно в транзакции удалить индекс `optp_objects_fire_unit_id_idx`, поле `optp_objects.fire_unit_id` и таблицу `optp_fire_units`. Не используйте CASCADE. Миграция не меняет существующие документы, схемы этажей, storage и политики объектов.

## Наполнение базы по подразделениям

В разделе подразделения администратор или редактор может создать объект кнопкой «+ Объект»; выбранное подразделение подставляется автоматически.

Для добавления сразу нескольких объектов:
1. Выберите нужное подразделение на главной странице.
2. Нажмите «Скачать шаблон CSV» и заполните его в Excel (одна строка — один объект).
3. Сохраните файл как CSV UTF-8 (разделитель — точка с запятой).
4. Выберите файл и нажмите «Проверить файл» — появится предпросмотр, повторы пропускаются по названию и адресу в пределах подразделения.
5. Нажмите «Добавить объекты в базу». Записываются только новые карточки объектов в `optp_objects` с существующим `fire_unit_id`. Вложенные PDF, Word и поэтажные планы загружаются отдельно из карточки объекта.

Импорт ограничен 200 объектами на файл; возможна частичная запись при сетевых ошибках — приложение сообщает число добавленных записей. Инструмент использует существующие Supabase Auth и RLS, не меняет схему и не предоставляет гостям права записи.

**Безопасность:** фильтрация по подразделению — это навигация, не ограничение доступа. Перед загрузкой служебных оперативных документов необходимо проверить политику RLS и доступ к файлам Storage. Не включайте публичное чтение конфиденциальных планов без соответствующего разрешения.

## Удаление объекта целиком

Войдите как **администратор**, откройте карточку объекта и нажмите **«Удалить объект»**. Для защиты от случайного удаления нужно ввести название объекта точно, затем подтвердить необратимое действие. Гости и редакторы не видят кнопку.

**Первоначальная настройка:** выполнить вручную один раз SQL из `supabase/migrations/202611060004_delete_object.sql` через Supabase SQL Editor. Функция `optp_admin_delete_object` проверяет роль `admin` на стороне базы, удаляет запись объекта и связанные записи из `optp_documents` и `optp_floor_plans` в одной транзакции и возвращает пути прикреплённых файлов. После этого приложение удаляет файлы из Supabase Storage (`optp-files`). Если у учётной записи нет разрешений на удаление файлов в Storage, объект удалится из базы, но останутся осиротевшие файлы; приложение покажет предупреждение для очистки через Storage Dashboard. Перед использованием проверьте политику Storage DELETE, RLS и создайте резервную копию. Удаление не подлежит отмене.

### Проверка перед удалением

Кнопка «Удалить объект» сначала отправляет безопасный проверочный запрос `optp_admin_delete_object(p_object_id := NULL)`: ожидаемая ошибка «Не указан объект» подтверждает наличие функции и права администратора. Запрос не удаляет никакие объекты. Если функция отсутствует (`PGRST202`) или прав недостаточно (`42501`), ошибка показывается рядом с кнопкой вместе со ссылкой на SQL-миграцию. Встроенная форма в карточке объекта требует точное название и галочку подтверждения. После этого приложение проверяет наличие SQL-функции и права администратора через безопасный запрос с NULL, а затем выполняет удаление. Всплывающие окна браузера для удаления больше не используются. Текст ошибки и коды также доступны в верхнем статусе.

**Важное ограничение:** публикация GitHub Pages не устанавливает SQL-функцию в Supabase. После обновления фронтенда необходимо выполнить миграцию `supabase/migrations/202611060004_delete_object.sql` в SQL Editor, если функция ещё не создана. Для проверки без удаления есть отдельная кнопка «Проверить удаление». Логика хранения и таблицы схем не изменяются.
